# 云端同步

目标:**没有登录流程,也能多设备同步、换设备找回数据。** 用「存档码」代替账号。

## 工作方式

- 第一次打开时,本机静默生成一个存档码(80 位随机,形如 `K7MQ-X2PD-9WTR-4HJF`),存在 localStorage。用户什么都不用做。
- 服务器只收到存档码的 SHA-256(下面叫 key),数据按 key 归属,**数据库里没有存档码本身**。
- 换设备:在「个人 → 存档与同步」或新手引导页输入存档码,云端数据会和本机已有数据**合并**,不会覆盖。
- 没配置 Supabase(没有 `.env.local`)时,同步和相关界面整体隐藏,app 照常本地使用。

## 本地优先

页面永远读写本地存档,同步引擎(`src/sync/engine.ts`)在后台对齐,所以**离线照常签到**,联网后自动补推。

每一轮同步:`(若有待通知的清空)→ 拉取云端变动并合并 → 把本地新增的推上去`。触发时机:本地有变动(防抖 1.5 秒)、恢复联网、回到页面、每分钟轮询。

只同步**原始数据**:签到记录、资料(昵称/头像/当前角色)、角色的拥有与毕业状态。经验、形态、连续天数不同步,一律由 `recomputeAll` 重算,所以规则调整不会让云端数据过期。

## 合并规则(`src/sync/merge.ts`)

| 数据 | 规则 |
|---|---|
| 签到记录 | 只增不改、id 唯一,按 id 取并集。同一天两台设备各签一次时,合并后只保留最早的一条计经验(`normalizeState`) |
| 角色进度 | 取并集;毕业状态只会 false → true |
| 资料 | 后写者胜(客户端毫秒时间戳) |
| 清空 / 恢复 | 见下 |

## 清空全部数据(软删除)

「个人 → 清空全部数据」,需输入「清空」确认。

- 本机立刻清空;云端把所有行打上 `deleted_at`,并记下 `cleared_at` 和清空前的资料。**软删除:行还在,30 天后由定时任务永久清除。**
- **30 天内可以「恢复清空的数据」**:清空之后,个人页(以及清空后回到的启动页)会出现恢复入口。
  恢复只还原那一次清空删掉的行;清空之后又产生的新数据原样保留,新旧合并;资料以现在的为准,没有才用清空前的。别的设备下次同步也会拿回数据。
- 超过 30 天,数据被永久清除,恢复入口消失。
- 存档码本身不变:清空后用同一个存档码恢复,拿到的是清空后的(空)数据,**恢复清空要用上面的入口,不是输入存档码**。
- 其他设备下次同步发现 `cleared_at` 晚于自己上次同步的时间,就清掉本地。
- 只有**同步过的设备**才会被清掉;新设备带着本地数据去恢复一个被清空过的存档码,本地数据不受影响。
- 离线时点清空:本地先清,联网后**先通知服务器**再拉取,不会把旧数据带回来。
- 进度的删除标记不会被逐条应用(只靠 `cleared_at` 整体清空),否则用户清空后立刻重选同一只角色会被旧标记误删。

## 验证存档码

- 个人页「存档与同步」里的「检查云端数据」会直接向服务器拉取这个存档码的全量数据(不合并、不改任何东西),显示云端的记录数、角色数和昵称。这是**不换设备**就能确认云端真的有数据的办法。
- 想完整演练「换设备」:用无痕窗口打开,在启动页输入存档码。同一个浏览器测不出来,因为它本来就绑着这个码。
- 测试前别点「清空全部数据」,清空会把云端的数据一起标记删除。

## 安全模型

- 表全部开启 RLS 且**不建任何 policy**,前端的 key 无法直接读写表,只能调用 `sync_pull / sync_push / vault_clear` 三个 security definer 函数,函数里校验 key 格式并按 key 取数。
- 前端用的是公开的 anon / publishable key,它本来就会出现在浏览器里;权限完全由数据库函数把关。
- **谁拿到存档码,谁就能读写那份数据。** 存档码高熵无法猜测,但不能泄露:分享卡片、日志、URL 里都不会出现它。
- 没有"找回存档码"的途径(没有邮箱和密码)。所以个人页有显眼的提示,签满 3 天首页会提醒一次保存。
- 防滥用只做了基础限制(key 格式、单次推送条数上限)。如果以后被刷,可以加 Supabase 的 Edge Function 限流。

## 部署步骤

1. 在 [supabase.com](https://supabase.com) 新建项目,Project Settings → API 里拿到 Project URL 和 anon / publishable key。
2. 复制 `.env.example` 为 `.env.local`,填入这两个值。**不要填 service_role / secret key。**
3. 打开 Supabase 控制台 SQL Editor,把 [supabase/migrations/0001_sync.sql](../supabase/migrations/0001_sync.sql) 整份贴进去执行(可重复执行)。
4. 运行 `node scripts/check-supabase.mjs` 联调检查,应全部 ✓。
5. 如果 SQL 末尾提示 `pg_cron 不可用`:到 Database → Extensions 启用 `pg_cron`,再执行一次 SQL。不启用不影响同步,只是软删除的数据不会自动清除。
6. `npm run dev`,在个人页看到「已同步」即成功。

## 改动注意

- **改 SQL 时同步改 `src/sync/__tests__/fakeBackend.ts`**(内存版服务器,行为要和 SQL 对齐),并重新跑 `scripts/check-supabase.mjs`。
- 单元测试(`src/sync/__tests__/sync.test.ts`)覆盖多设备合并、离线、清空等场景,但**跑的是内存版服务器,不是真 SQL**,所以联调脚本不能省。
- 同步状态和业务存档分开存(`poopoo-diary:sync:v1`),清除 localStorage 会同时丢掉存档码,务必提醒用户保存。
